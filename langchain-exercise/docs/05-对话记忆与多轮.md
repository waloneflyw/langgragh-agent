# 05 — 对话记忆与多轮会话

> 目标：掌握**让机器人"记住"上下文**的机制。这是把"单次问答"升级为"聊天机器人"的关键一步，
> 也是后面 Agent 能持续对话的基础。

---

## 1. 问题：模型天生"失忆"

看这段对话的尴尬：

```python
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

print(llm.invoke("我叫小明").content)          # 好的小明
print(llm.invoke("我叫什么？").content)        # ❌ 我不知道，因为你没告诉过我
```

原因：**每一次 `invoke` 都是独立的、无状态的**。模型不记得上一轮说过什么。
要让它能"记住"，必须**把历史消息手动带过去**。

---

## 2. 手动实现：把历史塞进消息列表

最朴素的做法——自己维护一个消息列表：

```python
from langchain_core.messages import SystemMessage, HumanMessage, AIMessage

messages = [SystemMessage(content="你是助手")]

# 第一轮
messages.append(HumanMessage(content="我叫小明"))
reply = llm.invoke(messages)
messages.append(reply)                        # 把模型回复也存起来
print(reply.content)

# 第二轮
messages.append(HumanMessage(content="我叫什么？"))
reply = llm.invoke(messages)
print(reply.content)   # ✅ 你叫小明
```

**这就是"记忆"的全部秘密**：把历史消息追加到列表，每次都把完整列表发给模型。
后面所有高级记忆组件，本质都是"帮你自动化管理这个列表"。

> 🔑 面试关键认知：**LLM 的"记忆"不是真记忆，而是"把历史塞回 prompt"**。

---

## 3. 用 ChatMessageHistory 管理历史

手动 append 不够优雅，LangChain 提供了专门的历史容器：

```python
from langchain_core.chat_history import InMemoryChatMessageHistory

history = InMemoryChatMessageHistory()

# 添加消息
history.add_user_message("我叫小明")
history.add_ai_message("你好小明")

# 读取全部历史
print(history.messages)   # [HumanMessage(...), AIMessage(...)]
```

常用的历史实现：

| 类 | 存储位置 | 适用 |
|----|---------|------|
| `InMemoryChatMessageHistory` | 内存 | 单进程、学习测试 |



> "InMemory" 意味着**重启就丢**。生产环境要换数据库或 Redis 实现。

---

## 4. 核心组件：RunnableWithMessageHistory

手动管历史，每轮都要自己"读历史 → 拼消息 → 调模型 → 存历史"，很繁琐。
`RunnableWithMessageHistory` 把这个流程**自动化**了：

```python
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.chat_history import InMemoryChatMessageHistory
from langchain_core.runnables.history import RunnableWithMessageHistory
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是乐于助人的助手"),
    MessagesPlaceholder("history"),     # 历史消息自动注入到这里（02篇讲过）
    ("human", "{input}"),
])

chain = prompt | llm

# ① 定义一个"会话ID → 历史记录"的存储（每个用户一条独立历史）
store = {}

def get_history(session_id: str):
    if session_id not in store:
        store[session_id] = InMemoryChatMessageHistory()
    return store[session_id]

# ② 包装：告诉它历史放哪、往哪个占位符里填
with_history = RunnableWithMessageHistory(
    chain,
    get_history,                    # 获取历史的函数
    input_messages_key="input",     # 用户输入在哪个 key
    history_messages_key="history", # 历史往哪个占位符填
)

# ③ 调用时要传 session_id（区分不同用户/会话）
print(with_history.invoke({"input": "我叫小明"}, config={"configurable": {"session_id": "user-1"}}).content)
print(with_history.invoke({"input": "我叫什么？"}, config={"configurable": {"session_id": "user-1"}}).content)
# ✅ 第二句能答出"你叫小明"
```

```
执行流程（全自动）：

invoke({"input": ...}, session_id)
        │
        ▼
① 按 session_id 取出历史 → 填入 history 占位符
② 调模型
③ 把本轮 input + 回复 追加进历史
        │
        ▼
返回回复
```

> 🔑 **`session_id` 是关键**：它让"不同用户/不同会话"拥有**各自独立**的记忆。
> 没有它，所有用户会共享同一份历史（灾难）。这个机制在多用户 Web 应用里至关重要。

## 5. 完整示例：能记事的客服机器人

```python
# 05_demo.py
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.chat_history import InMemoryChatMessageHistory
from langchain_core.runnables.history import RunnableWithMessageHistory

load_dotenv()
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是电商客服，回答简洁，记住用户说过的话。"),
    MessagesPlaceholder("history"),
    ("human", "{input}"),
])
chain = prompt | llm

store = {}
def get_history(session_id):
    if session_id not in store:
        store[session_id] = InMemoryChatMessageHistory()
    return store[session_id]

bot = RunnableWithMessageHistory(
    chain, get_history,
    input_messages_key="input", history_messages_key="history",
)

# 模拟一个用户的连续对话
session = {"configurable": {"session_id": "u-10086"}}
for q in ["我的订单号是A123", "帮我查一下这个订单", "我还买了什么？"]:
    print(f"用户: {q}")
    print(f"客服: {bot.invoke({'input': q}, config=session).content}\n")
```

跑起来你会发现，第三句它能根据前面的"订单号A123"来回答——记忆生效了。

## 6. 记忆的隐患：上下文越来越长

对话越长，历史越多，token 越多 → **更贵、更慢、还可能超出模型上下文窗口**。
解决方案是**裁剪历史**，常用两种：

### 6.1 只保留最近 N 条

```python
from langchain_core.runnables import RunnableLambda

# 裁剪函数：只留最近 6 条
def 裁剪(messages):
    return messages[-6:]

chain = prompt | llm
# 用 RunnableLambda 在调用前裁剪
裁剪链 = RunnableLambda(裁剪) | prompt | llm
```

### 6.2 按 token 数裁剪（更精确）

```python
from langchain_core.messages import trim_messages

trimmer = trim_messages(max_tokens=100, strategy="last", token_counter=llm)
```

> 生产中常见方案是：保留最近 N 条 + 用"总结器"把更早的对话压缩成摘要。
> 这是"长期记忆 vs 短期记忆"的平衡，面试可聊。

## 7. 记忆类型速查（面试高频）

LangChain 曾有一堆 Memory 类，现在主流是上面的 **RunnableWithMessageHistory + 消息裁剪** 方案。
但面试仍可能问旧概念，了解对应关系即可：

| 记忆策略 | 含义 | 现状 |
|---------|------|------|
| 缓冲记忆 Buffer | 记住所有历史 | 简单，会爆上下文 |
| 窗口记忆 Window | 只记最近 N 条 | 常用 |
| 总结记忆 Summary | 把旧对话总结成摘要 | 长期记忆方案 |
| 混合记忆 | 摘要 + 窗口结合 | 生产常用 |

---

## 8. 常见坑

| 坑 | 现象 | 解决 |
|----|------|------|
| 忘传 `session_id` | 报错或所有用户共享历史 | 每个用户/会话传独立 id |
| 历史没持久化 | 重启丢失 | 用 `SQLChatMessageHistory` 等持久化实现 |
| 历史无限增长 | token 爆炸、超限 | 裁剪或总结历史 |
| `history_messages_key` 写错 | 和 `MessagesPlaceholder` 对不上 | 两者名字保持一致 |

## 9. 面试高频题

**Q1：LLM 为什么"记不住"上一轮对话？如何让它记住？**
> A：因为每次调用都是无状态的，模型不会自动保存历史。办法是把历史消息（用户+助手）追加到消息列表，
> 每次调用时把完整列表发给模型。本质是"把历史塞回 prompt"，而非模型真有记忆。

**Q2：`RunnableWithMessageHistory` 的作用和用法？**
> A：它把"读历史→拼装→调模型→存历史"自动化。用法上需要提供 `get_history(session_id)` 函数、
> 指定 `input_messages_key` 和 `history_messages_key`，调用时通过 `config` 传 `session_id` 区分会话。

**Q3：多用户场景下为什么要用 `session_id`？**
> A：不同用户/会话必须有独立的历史存储，`session_id` 就是区分它们的 key，
> 保证用户 A 的对话不会串到用户 B 的记忆里。

**Q4：对话历史太长怎么办？**
> A：用裁剪策略（只保留最近 N 条、按 token 数裁剪）控制短期记忆长度，
> 或用"总结器"把更早对话压缩成摘要作为长期记忆，两者常结合使用。
